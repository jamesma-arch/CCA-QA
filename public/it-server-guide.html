English

Build and publish: npm ci → npm test → npm run build → serve dist/

  1. Build and publish. Use Node 22 or a maintained compatible runtime. Run npm ci, npm test and npm run build. Serve dist/ through the school's HTTPS web server; the build copies public files and bundles app.js.
  2. Move the API and records. Adapt netlify/functions/api.mjs and netlify/lib/core.mjs to a school Node HTTP service. Change the frontend API URL from /.netlify/functions/api to a same-origin /api/qa endpoint, preserving action parameters. Replace @netlify/blobs with a school-managed database adapter implementing the existing list, get and setJSON operations. Migrate activity/, review/ and followup/ records, include approved seed activities, and keep staging separate from production.
  3. Configure access and sessions. Set STAFF_ACCESS_CODE, ADMIN_ACCESS_CODE and SESSION_SECRET in the protected API service environment. Staff and admin codes must differ; SESSION_SECRET must contain at least 32 characters. Preserve HttpOnly, Secure, SameSite=Strict cookies, server-side staff/admin restrictions, same-origin checks and request limits. Replace platform rate limiting with school API/proxy limits. Shared codes are the current access model; SSO is a separate implementation.
  4. Validate QA records. Test staff submission and administrator import/analytics/follow-up. Confirm staff cannot retrieve private review analytics or use admin actions. Test mid-season and end-of-season reviews across seasons 1–3, flags below 4/5 and requested follow-up. Check records survive a restart and restore; retained activity IDs must still link historical reviews correctly.

For every build: assign a separate school HTTPS origin and staging environment; keep secrets in the API service environment; preserve security headers, origin checks and role restrictions; configure service supervision, monitoring, backup/restore and rollback. Verify migration with school IT before using real records.

ภาษาไทย

คำสั่งสร้างและเผยแพร่: npm ci → npm test → npm run build → serve dist/

  1. สร้างและเผยแพร่เว็บไซต์. ใช้ Node 22 หรือ runtime ที่รองรับและยังได้รับการดูแล รัน npm ci, npm test และ npm run build ให้เว็บเซิร์ฟเวอร์ HTTPS ของโรงเรียนให้บริการ dist/ กระบวนการ build คัดลอกไฟล์ public และรวม app.js
  2. ย้าย API และข้อมูล. ปรับ netlify/functions/api.mjs และ netlify/lib/core.mjs ให้ทำงานใน Node HTTP service ของโรงเรียน เปลี่ยน URL ฝั่งหน้าเว็บจาก /.netlify/functions/api เป็น /api/qa บน origin เดียวกัน โดยคงพารามิเตอร์ action แทนที่ @netlify/blobs ด้วยตัวเชื่อมต่อฐานข้อมูลโรงเรียนที่รองรับ list, get และ setJSON ย้ายข้อมูล activity/, review/ และ followup/ รวมกิจกรรมเริ่มต้นที่ได้รับอนุมัติ และแยกระบบทดสอบจากข้อมูลจริง
  3. ตั้งค่าสิทธิ์และเซสชัน. เก็บ STAFF_ACCESS_CODE, ADMIN_ACCESS_CODE และ SESSION_SECRET ใน environment ของ API ที่ป้องกันไว้ รหัสบุคลากรและผู้ดูแลต้องต่างกัน SESSION_SECRET ต้องยาวอย่างน้อย 32 อักขระ คง cookie แบบ HttpOnly, Secure, SameSite=Strict การจำกัดสิทธิ์ฝั่งเซิร์ฟเวอร์ การตรวจสอบ origin และขนาดคำขอ ตั้ง rate limit ที่ API/proxy ของโรงเรียนแทนข้อจำกัดของแพลตฟอร์มเดิม ระบบปัจจุบันใช้รหัสร่วมกัน หากต้องการ SSO ต้องพัฒนาแยก
  4. ตรวจสอบข้อมูล QA. ทดสอบส่งแบบประเมินด้วยบัญชีบุคลากร และนำเข้า/วิเคราะห์/ติดตามด้วยผู้ดูแล ตรวจสอบว่าบุคลากรดึงข้อมูลวิเคราะห์ส่วนตัวหรือใช้คำสั่งผู้ดูแลไม่ได้ ทดสอบประเมินกลางและปลายฤดูกาลในฤดูกาล 1–3 การแจ้งเตือนคะแนนต่ำกว่า 4/5 และคำขอติดตาม ตรวจสอบข้อมูลยังอยู่หลัง restart และกู้คืน และ ID กิจกรรมเดิมยังเชื่อมกับประวัติการประเมิน

สำหรับทุก build: กำหนด HTTPS origin ของโรงเรียนและระบบทดสอบแยกต่างหาก เก็บข้อมูลลับใน environment ของ API คง security headers การตรวจสอบ origin และสิทธิ์ตามบทบาท ตั้งค่าระบบดูแลโปรเซส การติดตาม สำรอง/กู้คืน และ rollback ให้ IT ตรวจสอบการย้ายระบบก่อนใช้ข้อมูลจริง
